# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Setup and running

Python >=3.12, managed with `uv` (`uv.lock`, `.venv`). There is no test suite or linter config. `README.md` covers setup and features for users.

- Install: `uv sync`
- Run the demo workbench: `uv run python src/run_workbench.py` (127.0.0.1:8000, admin/`1234`; host UI at `/ui/`). Workers join it with the workbench's URL plus an invite code created in its UI. The workbench's `public_url` must equal the URL the worker joined with.
- Run the demo worker: `uv run python src/server.py` (serves on 127.0.0.1:9999; `src/` is the import root, so run from the repo root or put `src` on `PYTHONPATH`). It builds an `AgenticWorker` with `AnthropicProvider` and a placeholder `model="xxx"`, so set a real model ID and provider credentials before expecting LLM output.
- Admin password comes from the `admin_password=` argument to `.run()` or the `ADMIN_PASSWORD` env var.

## Architecture

The project is a framework for building **A2A (Agent-to-Agent) worker agents** that can join a central "workbench" server. Package `src/workbench/`:

- `worker/worker_server.py`: `WorkerServer(AgentExecutor)` is the base class. Subclasses implement `run_task(context, event_queue, workbench)`. It exposes:
  - an A2A JSON-RPC endpoint at `/a2a/`, protected by bearer tokens
  - a public Agent Card at `/.well-known/agent-card.json`
  - an admin API at `/admin/*` (session cookie plus CSRF, or HTTP Basic)
  - a web UI at `/ui/`, served from `worker/ui/` (plain `index.html`/`app.css`/`app.js`; the CSP in `web_auth.py` forbids inline scripts and styles). It uses the admin API. `checkConnection` calls `GET /admin/workbench/status` (which pings the workbench). Join requests the workbench denied are kept only in the browser's localStorage
- **btw (messages while a task runs):** `extensions.py` defines the extension. A worker class with `supports_btw = True` (`AgenticWorker`) declares it in its agent card, keeps an inbox per running task (`WorkerServer.take_messages` / `close_inbox`), and reads it only between steps (after a generation and after tool results; a message that arrives during the final generation makes the loop continue instead of finishing). The workbench does not send a second A2A `message/send`: the installed a2a SDK would start a second concurrent `execute()` for the same task and its cleanup closes the running task's event queue. Instead `TaskManager._send_btw` POSTs `{task_id, text}` to `<a2a url>/btw` (a route on the worker's A2A app, same bearer auth, owner-checked), so `POST /admin/tasks/{id}/message` and `/wb/api/v1/tasks/{id}/message` work for running tasks too (409 if the agent lacks the extension, the task has just started or is finishing). The workbench learns support from the agent card (`btw` on the worker record, via `_refresh_card`), logs `btw` and `btw_applied` events, and the task panel shows a message box when `accepts_btw`.
- `worker/agentic_worker.py`: `AgenticWorker(WorkerServer)` is the LLM agent loop. It streams LLM text, runs requested tools, and repeats up to `max_tool_rounds`. It reports progress as A2A status updates (tool-call data parts) and streams the answer as the `"answer"` artifact. Conversation history is in memory, keyed by A2A `context_id`.
- `worker/llm_providers.py`: provider-neutral `LLMProvider` ABC with `AnthropicProvider` and `OpenAIProvider`. It defines shared types (`ChatMessage`, `ToolCall`, `ToolResult`, `TextDelta`, `LLMResponse`) and converts them to each vendor's message format.
- `worker/tools.py` and `worker/predef_tools.py`: the `Tool` ABC (`Parameter` list plus `execute`, sync or async) and built-ins `BashTool` (timeout and command allowlist) and `ListParticipantsTool` and `DelegateTool`, which reach the caller's workbench through `worker/context.py` (a ContextVar that `WorkerServer.execute` sets around `run_task`). Tools can be toggled at runtime through the admin API.
- `worker/web_auth.py`: session store, login rate limiter, security-headers middleware, and origin checks for the admin UI.
- `worker/__init__.py`: re-exports the public API, so scripts can use `from workbench.worker import *`.
- `workbench.py`: `WorkbenchClient`, a client for the workbench's public API (`/wb/api/v1/...`, authenticated with a workbench **API token**; ping, participants, task delegation and follow-up messages). It is meant for third-party programs and has nothing to do with joining. Responses are pydantic models that truncate untrusted text.
- The join handshake lives in `WorkerServer` (`worker_server.py`), not in `workbench.py`. It has its own `WorkbenchInfo`/`JoinResponse` models. `WorkbenchConnection` wraps a `WorkbenchClient` and is the object passed to `run_task` as `workbench`. It deliberately hides the token. Besides `participants()` it offers `start_task`, `get_task`, `cancel_task` and `run_task` (start and wait), which delegate through the workbench.
- `server/`: `WorkbenchServer`, the central workbench (`run_workbench.py` is a demo). Workers never talk to each other. They ask the workbench to start tasks on other workers, and it relays them over A2A.
  - `server.py`: the FastAPI app with three route groups. `/admin/*` is for hosts (username and password, session cookie plus CSRF, like the worker). `/wb/worker/v1/*` is the join handshake (`info`, `join`, `join/{request_id}`, `leave`). `/wb/api/v1/*` is for member workers, authenticated with their workbench token (`ping`, `participants`, `tasks` (start, and list by `scope`), `tasks/{id}?wait=N`, `tasks/{id}/message`, `tasks/{id}/cancel`). The UI is in `server/ui/` (plain files, strict CSP, shared code in `common.js`): `index.html` lists agents, invites and root tasks, and `task.html` draws one task tree as SVG with a live log panel for the selected node. `GET /admin/tasks/{id}/events?after=N` is polled for that log. Agent icons come from the A2A agent card's `icon_url` (a worker sets it through `icon_url=` or `PATCH /admin/card`). The workbench fetches the image itself (data: URI, or the worker's own origin only) and serves it at `/icon/{worker_id}`, so browsers never load worker-supplied URLs. Agents without an icon get a globe.
  - `tasks.py`: `TaskManager` runs each delegated task as a background asyncio task that streams the worker's A2A response into the store. Each task is a node with `root_id`, `parent_id` and `depth`. A worker names the task it is working on as `parent_task_id`, and receives its own id in the A2A request's `metadata.workbench.task_id`. `send_message()` resumes a task that is `input_required`. A finished task is continued by starting a new root with the same `context_id`. There is no separate interrupt; cancel is the interrupt. Tasks get a `topic` from `make_topic` (first sentence of the input, replaceable through `TaskManager.topic_fn`). A task counts as "waited" while its requester has a long poll of it in flight (`polling()`), which the tree view draws as a solid arrow and an hourglass. `cancel()` cancels the whole subtree, deepest first and the requested task last. It sends A2A `cancel_task` to the worker (best effort) and cancels the local runner.
  - `labels.py` and `settings_api.py`: labels, communication rules, general settings and API keys (admin endpoints in `settings_api.py`, UI in `ui/settings.html` + `settings.js`, opened with the gear icon). Every worker has at least one label, and a joining worker gets a fresh label named after it. The communication policy is `open` (default) or `restricted`, where directed (from label, to label) pairs say who may hand work to whom. It is enforced in `POST /wb/api/v1/tasks` (403) and filters `participants` for worker callers. Hosts and API keys are exempt. Settings the host can change at runtime (name, description, task limits, communication) live in the store's settings record. The constructor takes no name or description. On first boot `_load_settings` (run from the app lifespan, since the store is async) writes the defaults ("My Workbench", no description) into the store, and on every boot it loads the stored values into `self.name` and `self.description`. The workbench URL is fixed. An API key (`wbk_...`, stored hashed) authenticates `/wb/api/v1` for outside programs using `WorkbenchClient`: it starts root tasks only, with no sub-tasks, and sees only the tasks it started.
  - `board.py` and `board_api.py`: the shared board (step 1 of a plan to let agents coordinate peer to peer through a shared medium instead of only delegating). Hosts create channels (agents cannot, so no hidden channels); `read_label_ids` / `write_label_ids` say which labels may read or write each one (empty = everyone); every worker has an implicit private mailbox `@<worker id>` that others may write to if the label communication rules allow. The sender of a message is set from the authenticated token (worker, `host` or API key `api`), never from the request. Messages are append-only with one global `seq` across channels, so a single cursor follows everything (`GET /wb/api/v1/board/feed?after=N&wait=S`, long poll via an in-process `asyncio.Condition`). Posting is rate limited per sender (`board_rate_per_minute` setting). Hosts and API keys see every channel and mailbox; the host UI `board.html` follows it live and can post as host; channels are managed in settings (Board section). Worker tools: `BoardChannelsTool`, `BoardPostTool`, `BoardReadTool`, `BoardWaitTool` (they label message content as untrusted information). Not built yet: waking agents on mentions, shared files, `HumanWorker`, pause/kill and budgets.
  - `store.py`: abstract `WorkbenchStore` (async CRUD over plain dicts, record shapes in its docstring; it also keeps a per-task event log: input, state changes, tool calls reported as A2A data parts, delegations) (plus labels, API keys and settings) with `InMemoryStore`, the only implementation. Pass another via `WorkbenchServer(store=...)`.

### Workbench and auth model

- `join_token.py`: a join token (`wbj1.` plus base64url JSON of workbench URL and invite code) is a one-string alternative to entering URL and code. The workbench returns one from `POST /admin/invites`, and the worker's `POST /admin/workbench/join` accepts `join_token` or `base_url` + `invite_code`. It is unsigned, because the invite code is the only secret.
- Join flow on the workbench side: a host creates an invite (only its hash is stored), and the worker posts it with its URLs and a fresh inbound token. Unless the invite auto-approves, the join stays `pending` until a host approves it. The worker then collects its workbench token exactly once by polling. The workbench keeps only the token's hash, but must keep each worker's inbound token in plain text to call it.
- Each inbound token is bound to at most one workbench. The request's workbench is derived from the authenticated token. `metadata.workbench.url` is only cross-checked, never trusted.
- Joining uses a token exchange. The worker sends a fresh inbound token (so the workbench can call it) plus an invite code, and receives a token to call the workbench. Either side can revoke independently. Tokens are stored hashed (`_hash_token`).
- Workbench URLs are validated by `_check_workbench_url`. Plain HTTP is allowed only for loopback unless `allow_insecure_workbenches=True` is passed to `.run()`.
- Admin-saved state (card, skills, tool toggles, tokens, joined workbenches) persists in `<slug>.state.json` (or `state_file=`) in the working directory. It takes precedence over constructor arguments and is written atomically through a `.tmp` file plus `os.replace`.
